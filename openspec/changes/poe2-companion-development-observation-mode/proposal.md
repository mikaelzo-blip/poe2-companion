# Proposal: Development Observation Mode

## Why

Developing and tuning the Path of Exile 2 Companion requires real gameplay evidence to identify parser gaps (such as unhandled `Client.txt` formats like DEF-01), detect noisy objective churn, assess notification utility, and understand real-world state transitions. However, testing during live play must never distract the player, violate game automation rules, or perturb the continuous runtime.

Currently, diagnosing runtime edge cases requires manual log inspection or post-hoc log reconstruction. Development Observation Mode introduces a passive, privacy-safe, read-only observation tap that attaches to the existing continuous runtime. It records structured session telemetry, state deltas, objective decision traces, notification outcomes, unknown log anomaly signatures, manual player markers, and optional event-triggered screenshots. Crucially, the observer is strictly subordinate to the continuous runtime: it operates through a bounded asynchronous pipeline that cannot block or crash runtime correctness, employs fail-closed privacy filters, guarantees atomic marker coordination without shared queue corruption, maintains recoverable session manifests across crashes, executes an orderly bounded shutdown drain without indefinite blocking, handles worker degradation gracefully, and enforces deterministic global retention that protects newly finalized sessions.

Furthermore, development observation cleanly decouples local live analysis from AI provider availability through a crash-consistent two-plane architecture:
1. **Local Live Analysis Data Plane**: A deterministic, read-only local process (`companion observe analyze-live`) operates under an at-least-once input and idempotent derived output contract. It continuously reads new structured evidence, maintains stream continuity across rotated segments, updates deterministic factual signals with stable identities (`local_signals.jsonl`), tracks persistent UNKNOWNs and churn patterns, manages pending review request generation, and advances its durable reader cursor (`reader_state.json`) strictly after successful output persistence, recovering independently of external AI availability.
2. **Actual Hermes AI Review Plane via Filesystem Review Bridge**: While the review-batch infrastructure was previously established, verification confirmed `REAL_HERMES_AI_WIRED = NO` because the initial implementation relied on a deterministic heuristic inside `LiveReviewEngine` (`if USER_MARKER: CREATE else NO_FINDING`) rather than real AI reasoning. To connect the actual Hermes agent during gameplay without embedding AI provider credentials, SDK dependencies, or LLM clients into the companion, the system introduces a durable **Filesystem Hermes Review Bridge**. The companion writes immutable review requests (`review_requests/<review_batch_id>.json`) including a bounded catalogue of existing findings; Hermes claims requests via claim-specific immutable claim artifacts (`review_claims/<review_batch_id>.<claim_id>.json`); Hermes inspects the request and persisted evidence, reasons using its active model, and writes claim-specific atomic structured review response candidates (`review_responses/<review_batch_id>.<claim_id>.json`); and the companion review bridge coordinator validates claimant provenance, complete evidence accounting, safe targeted privacy, and finding identity rules before promoting the winning candidate into a canonical `ReviewBatchResult` (`review_batches/<review_batch_id>.json`) and advancing the contiguous review cursor with reviewed-ahead range support (`hermes_review_cursor.json`).

This two-plane filesystem bridge model ensures that AI provider outages, context resets, or task terminations never affect the companion runtime or lose observation data, while enabling genuine real-time developer awareness during active gameplay, crash-consistent replay safety, and complete post-session synthesis upon closure.

## What Changes

- **Subordinate Continuous Runtime Observation Tap**: Attach an asynchronous, non-blocking read-only observer (`DevelopmentObserver`) to `ContinuousRuntimeOrchestrator` lifecycle callbacks. The observer is strictly subordinate and never participates in or blocks the correctness path for `Client.txt` ingestion, `CharacterState` reconciliation, checkpoint persistence, objective evaluation, notification delivery, or writer lease ownership. When disabled, the observer creates no background worker and performs zero storage I/O, introducing only negligible callback branch check overhead.
- **Strict Single-Runtime Invariant**: The observer is not a second game runtime; it never instantiates a duplicate `ProcessMonitor`, `ClientLogTailer`, `CharacterStateStore` writer, or `ObjectiveEngine`.
- **Orderly Bounded Shutdown & Queue Drain Pipeline**: The observation session must never be marked `CLOSED` while queued evidence is unwritten. Shutdown enforces a strict 9-step sequence: (1) runtime initiates shutdown, (2) observer stops accepting new ordinary events, (3) bounded queue is drained, (4) pending screenshots are completed or cancelled/skipped, (5) JSONL writers are flushed and closed, (6) final counters and sequence watermarks reconcile, (7) session summary is generated, (8) manifest is atomically updated, and (9) only then may status become `CLOSED`. A bounded shutdown timeout (5.0s) guarantees the observer never blocks runtime shutdown indefinitely; if drain cannot finish within the timeout, the manifest is recorded as `INCOMPLETE` with `OBSERVER_DRAIN_TIMEOUT` and accurate pending/dropped counts, rather than claiming `CLOSED`.
- **Observer Health States & Worker Degradation**: Track explicit health states (`HEALTHY`, `DEGRADED`, `FAILED`). A fatal persistence worker failure never crashes the continuous runtime: observer health transitions to `FAILED`, new enqueues are rejected or safely discarded to prevent unbounded queue accumulation, and the manifest is marked `INCOMPLETE`. Screenshot worker failures degrade health to `DEGRADED` independently without disabling text/delta collection. Endless worker restart loops are forbidden.
- **Deterministic 3-Tier Priority Drop Policy**: Enforce deterministic queue shed behavior under backpressure:
  - `HIGH`: `ERROR`, parser anomalies, state deltas, user markers, objective changes
  - `MEDIUM`: notification decisions, ordinary parsed gameplay events
  - `LOW`: periodic performance telemetry, unchanged/no-op diagnostics
  When queue capacity is pressured, LOW evidence is dropped before MEDIUM before HIGH. If HIGH evidence must be dropped under extreme load, it is explicitly recorded in `dropped_high_priority_count` and data-loss metadata.
- **Correlation Integrity Under Dropped Evidence**: When upstream evidence (e.g. log observation A) is dropped under backpressure while downstream evidence (state delta B, objective trace C) survives, downstream envelopes record the dropped status or tombstone (`correlation_missing_due_to_backpressure`). Hermes review surfaces missing parent evidence under `MISSING_EVIDENCE` and prevents findings from being promoted beyond available support.
- **Canonical Evidence Envelope & Correlation Contract**: Define a stable evidence envelope across all observation streams featuring `schema_version`, unique `event_id`, strictly monotonic `sequence_number`, distinct `source_timestamp` and local `recorded_at`, fact taxonomy, and explicit `correlation_refs` linking the full causal chain: log observation -> state delta -> objective evaluation -> notification decision -> screenshot -> manual marker (forbidding loose heuristic timestamp matching).
- **Authoritative Marker IPC vs Persisted Marker Evidence**: Preserve the accepted cross-process marker architecture:
  - *Marker IPC*: `companion observe mark "<note>"` writes `runtime/observations/marker_inbox/<uuid>.tmp`, then executes an atomic rename to `<uuid>.json`. Concurrent CLI writers remain completely isolated via distinct UUID filenames. The continuous runtime `DevelopmentObserver` drains only complete `.json` files (ignoring `.tmp`), enriches them with active session and objective context, and reports inactive sessions honestly when no session is running.
  - *Persisted Marker Evidence*: The observer persists normalized marker evidence envelopes into `markers.jsonl` with full correlation metadata. Live analysis and Hermes consume this persisted evidence stream, NOT a shared append-only file as an IPC transport.
- **Fail-Closed Privacy for Log Anomaly Discovery**: Maintain strict filtering for whispers, chat channels, credentials, and tokens. Strengthen unknown-line discovery so representative text is persisted only when lines pass all filters, match an approved debug envelope, and sanitize completely. Any classification uncertainty triggers fail-closed behavior: representative text is withheld, setting `PRIVACY_SAMPLE_WITHHELD = true` and storing only normalized signature hashes, frequency counts, and timestamps.
- **Asynchronous Opt-In Screenshot Evidence**: Allow event-triggered screenshots (`--observe-screens`) via MSS with strict trigger filters, cooldowns, display targeting, and storage quotas. Capture requests are dispatched asynchronously to the observer worker so slow captures or failures (`SKIPPED_BUDGET`, `SKIPPED_COOLDOWN`, `CAPTURE_FAILED`) never block runtime ticks or mutate `CharacterState`.
- **Atomic Session Manifest & Manifest Reconciliation**: Maintain an atomically updated `session_manifest.json` tracking session status (`OPEN`, `CLOSED`, `INCOMPLETE`, `ABORTED`), high-watermark sequences, dropped event counts, and artifact counts. Total persisted records plus dropped events reconcile exactly against the sequence high watermark. Unfinalized prior sessions are safely detected on startup, marked `INCOMPLETE / ABORTED`, and preserved for partial post-session review.
- **Boundary Retention & Newly Closed Session Protection**: Enforce per-file JSONL rotation, screenshot quotas, and a deterministic global observation storage bound. Retention pruning executes strictly at session start, session close, or explicit CLI invocation (never during a gameplay tick). The active session, the session being finalized, and the newly closed session remain strictly protected through final summary/manifest completion, preventing premature deletion before review. Reports under `docs/audits/` are preserved permanently.
- **Observer Operational Performance Telemetry**: Measure enqueue latency, queue depth, dropped event count, writer latency, screenshot capture duration, and worker error counts using monotonic clock intervals.
- **Filesystem Hermes Review Bridge Architecture**:
  - Connect the local companion data plane to the actual external Hermes agent using a durable filesystem IPC bridge without embedding AI provider SDKs or API credentials in the companion repository.
  - The local data plane creates deterministic review batches and writes atomic, immutable review request files (`runtime/observations/<session>/live_analysis/review_requests/<review_batch_id>.json`).
  - The external Hermes agent inspects requests, acquires or touches an immutable, claim-specific claim artifact (`review_claims/<review_batch_id>.<claim_id>.json`), reads associated persisted evidence, performs genuine AI reasoning with its active model, and writes claim-specific atomic structured review response candidate files (`runtime/observations/<session>/live_analysis/review_responses/<review_batch_id>.<claim_id>.json`).
  - The companion review bridge coordinator validates incoming responses against claimant provenance and accounting rules, arbitrates deterministically (first valid response candidate promoted to canonical `ReviewBatchResult`), persists durable batch results (`review_batches/<review_batch_id>.json`), applies findings idempotently, and advances the contiguous review cursor with reviewed-ahead range support (`hermes_review_cursor.json`).
- **Immutable Review Request Artifact & Coordinator-Owned State**:
  - For every deterministic `review_batch_id`, the companion writes an immutable request artifact (`.tmp` -> `fsync` -> rename) containing `schema_version`, `review_batch_id`, `session_id`, `sequence_start`, `sequence_end`, ordered `evidence_ids`, `high_priority_signals`, `marker_refs`, `objective_refs`, `notification_refs`, `unknown_stale_refs`, `anomaly_refs`, `existing_findings` (sanitized bounded catalogue of existing findings to support UPDATE operations), `evidence_locations`, `privacy_instructions`, and `created_at`.
  - The request JSON file is strictly immutable once published; it is NEVER used as a mutable multi-writer state file.
  - Derived coordinator status (`PENDING`, `CLAIMED`, `RESPONSE_AVAILABLE`, `COMPLETED`, `FAILED_VALIDATION`, `RETRYABLE`) is managed in coordinator-owned state metadata, not by rewriting request files.
- **Separate Claim-Specific Artifact Lifecycle & Concurrency Arbitration**:
  - Claim artifacts are claim-specific and immutable: `runtime/observations/<session>/live_analysis/review_claims/<review_batch_id>.<claim_id>.json` containing `schema_version`, `review_batch_id`, `claim_id`, `review_run_id`, `claimed_at`, and `lease_expires_at`.
  - Claim artifacts MUST NOT be shared multi-writer files: each Hermes review run publishes its own atomic claim artifact, ensuring durable evidence of claimant identity is never overwritten.
  - Safe lease renewal without claim overwrite: if a review run needs heartbeat/lease renewal, it updates only state belonging to its own claim (such as `review_claim_status/<batch_id>.<claim_id>.json` or an atomic self-owned status file), never rewriting another claimant's claim file.
  - Claim leases use a conservative initial window (180s) or heartbeat renewal, accommodating slow provider/model reasoning cycles without false expiration.
  - Claimant validation: the coordinator validates that matching immutable review request exists, matching claim artifact exists, `claim.review_batch_id` matches request, `response.claim_id` matches claim, `response.review_run_id` matches claim, and accounting passes.
  - Arbitration policy: first valid response candidate promoted to canonical `ReviewBatchResult` wins.
  - Distinction between lease eligibility and response provenance: a stale claim may still produce a valid response; do not reject an otherwise valid completed response solely because its lease expired milliseconds before publication if it completes before another candidate is promoted.
  - Once one valid candidate is promoted to canonical `ReviewBatchResult`, all later candidates for that `review_batch_id` are ignored/quarantined without corrupting the canonical result.
  - A claim alone NEVER advances the review cursor or equates to completed review.
- **Non-Overlapping Review Request Coverage & Mutable Priority Scheduling**:
  - Strict coverage invariant: A global observation sequence may belong to AT MOST ONE canonical review request. Immutable review request ranges MUST NEVER overlap (e.g. 101–150, 151–200; never 101–150 and 140–175).
  - Priority does NOT create an overlapping batch: if a high-priority marker arrives for sequence 175 and sequence 175 already belongs to pending canonical request 151–200, the system promotes/prioritizes the EXISTING canonical request 151–200 rather than creating a marker-specific overlapping batch (e.g. 170–180).
  - If no request has yet been formed for the marker sequence, the next canonical non-overlapping request covering it is created according to deterministic batch partitioning, then marked high priority.
  - Priority metadata ownership: mutable scheduling priority is coordinator-owned metadata (`review_batch_id`, `priority` [NORMAL, HIGH_MARKER, HIGH_ERROR], `priority_reason`, `updated_at`) stored separately from immutable requests. Priority metadata affects which pending request Hermes selects first; it does NOT alter evidence ranges, batch IDs, immutable request payloads, or review frontiers.
  - Canonical request coverage mechanism & restart reconstruction: the coordinator maintains durable canonical non-overlapping sequence coverage in coordinator state/index (reconstructed deterministically on restart from request files). On companion restart, coverage is loaded before generating new requests; requests are NEVER generated for sequences already owned by PENDING, CLAIMED, RESPONSE_AVAILABLE, COMPLETED, or reviewed-ahead batches. Completed-ahead requests remain completed and are never regenerated.
  - Out-of-order review remains allowed: e.g. review frontier 100, pending request A (101–150 NORMAL) and B (151–200 HIGH_MARKER). Hermes may review B first; after B completes, `reviewed_ahead_ranges = [[151, 200]]` and frontier remains 100. When A completes, review frontier catches up to 200 contiguously.
- **Structured Review Response Schema & Full Evidence Accounting**:
  - Hermes writes a candidate artifact (`.tmp` -> `fsync` -> rename) named `<review_batch_id>.<claim_id>.json` containing `schema_version`, `review_batch_id`, `session_id`, `sequence_start`, `sequence_end`, `accounted_evidence_ids`, `claim_id`, `review_run_id`, `reviewed_at`, and an array of `operations`.
  - Full Evidence Accounting Rule: `accounted_evidence_ids` MUST exactly account for the request's expected reviewable evidence set (`set(response.accounted_evidence_ids) == set(request.evidence_ids)`). If evidence coverage is incomplete, the response is rejected, the cursor remains unchanged, and the request remains retryable.
  - Finding `evidence_refs` supporting a specific finding operation MAY be a subset of `accounted_evidence_ids`.
  - Allowed operations: `CREATE_FINDING`, `UPDATE_FINDING`, and `NO_FINDING`.
  - Finding Identity Model: For `CREATE_FINDING`, Hermes provides `category`, `semantic_issue_key`, `safe_summary`, and classification; the companion derives the stable logical `finding_id`. For `UPDATE_FINDING`, Hermes MUST provide an explicit `target_finding_id` pointing to an existing session finding from the provided `existing_findings` catalogue. Silent creation of duplicate findings from reworded semantic keys is forbidden.
  - Hidden chain-of-thought and scratchpads are strictly forbidden in response artifacts.
- **Strict Companion Ingress Validation Boundary & Targeted Privacy**:
  - The companion review bridge MUST NOT blindly trust review response files.
  - Ingress validation verifies: valid schema, expected `review_batch_id`, matching session ID, valid sequence bounds, exact evidence accounting match, valid target finding ID for updates, allowed operations enum, allowed finding classifications, and no path traversal or arbitrary filesystem references.
  - Targeted Privacy Gate: Replaces broad character blacklists (which previously rejected safe punctuation like `%` and `!`). Imposes targeted fail-closed detection for actual sensitive structures (whispers, `@From`, `@To`, chat prefixes, bearer/API tokens, credentials, private secrets, unbounded raw log dumps) and bounds field lengths (`safe_summary <= 300`, `corroboration_note <= 500`). Safe engineering phrases like `"Flameblast quality remained below 40%"` are valid.
  - Invalid responses reject cursor advancement, log review bridge errors, and keep the request pending/retryable.
- **Subordinate Review Cursor Ownership & Contiguous Frontier with Priority Requests**:
  - Hermes is strictly prohibited from directly writing or modifying `hermes_review_cursor.json` or CharacterState.
  - The deterministic companion review bridge alone owns cursor advancement.
  - Priority marker requests reviewed ahead of older routine requests DO NOT jump the durable review cursor: the completed priority batch is retained as durably reviewed-ahead state (`reviewed_ahead_ranges` in `hermes_review_cursor.json`), and the review frontier advances contiguously only after the older missing batch completes.
- **Disposition of LiveReviewEngine (Zero Fake AI)**:
  - The existing `LiveReviewEngine` is refactored into the `ReviewBridgeCoordinator`. The synthetic heuristic (`if USER_MARKER: CREATE else NO_FINDING`) is completely retired from production execution.
  - A deterministic test adapter (`TestReviewResponder`) is provided strictly for offline unit tests and CI, ensuring tests run reliably without fake AI pretending to be Hermes in production code.
- **Project-Local Live Observation Hermes Workflow / Skill & Write Allowlist**:
  - Provide a project-local Hermes skill/workflow (`poe2-live-observation`) for "Start live development observation".
  - Enforces the strict Hermes Write Allowlist: Hermes may write ONLY `review_claims/<review_batch_id>.<claim_id>.json`, optional self-owned lease renewal artifacts (`review_claim_status/<review_batch_id>.<claim_id>.json`), `review_responses/<review_batch_id>.<claim_id>.json`, and `hermes_review_status.json`. Hermes is strictly forbidden from editing companion source, tests, OpenSpec files, objective rules, CharacterState, observer evidence, reader state, or review cursor.
  - Instructs the actual Hermes agent to: (1) locate the active observation session, (2) poll `review_requests/` for pending requests, (3) prioritize markers, errors, and objective churn, (4) read local evidence and bounded `Client.txt` windows, (5) reason with the active LLM, (6) write claim-specific atomic responses, and (7) maintain heartbeat telemetry in bounded intervals.
- **Heartbeat-Grounded Liveness Telemetry**:
  - Hermes liveness is tracked in `runtime/observations/<session>/live_analysis/hermes_review_status.json` with a 30s freshness window.
  - Status is evaluated as `ACTIVE` strictly when a real Hermes task updates its heartbeat freshly; otherwise reports `OFFLINE / INACTIVE / STALE`. Local data plane activity never implies Hermes is active.
- **AI Provider Interruption, Task Resumption & Marker Priority**:
  - When Hermes terminates or the AI provider errors, continuous runtime and local data plane proceed unaffected, while request files remain safely queued.
  - On user command ("Resume live development observation"), Hermes discovers pending requests, skips already-completed batches, prioritizes marker requests before routine telemetry, and catches up cleanly.
- **Multi-Tier Live Observation Status UX**:
  - `companion observe live-status` displays three distinct tiers (OBSERVATION, LOCAL ANALYSIS, HERMES REVIEW), reporting pending and completed request counts, bridge errors, reader saturation state, and separate reader and review lag values derived strictly from contiguous frontiers.

## Capabilities

### New Capabilities
- `development-observation`: Read-only, privacy-safe development evidence collection, objective decision tracing, anomaly discovery, manual markers, bounded asynchronous storage, post-session review packaging, and filesystem Hermes review bridge with response validation.

### Modified Capabilities
*(None - continuous runtime requirements and behavior remain unchanged when observation mode is disabled or attached).*

## Impact

- **Affected Code**:
  - `companion/runtime/orchestrator.py`: Register optional non-blocking `ObservationTap` callbacks and bounded shutdown/drain hook.
  - `companion/runtime/models.py`: Add observation configuration options (`observe_dev`, `observe_screens`, observation paths).
  - `companion/observe/models.py`: Add `ReviewRequestEnvelope`, `ReviewResponseEnvelope`, finding operation models, and request state enums.
  - `companion/observe/bridge.py` (or `companion/observe/live_reviewer.py`): Refactor `LiveReviewEngine` into `ReviewBridgeCoordinator`, add atomic request writer, response consumer, ingress validation gate, and offline test adapter.
  - `companion/observe/cursor.py`: Validate that cursor advancement remains strictly owned by the companion review bridge.
  - `companion/observe/analyst.py`: Coordinate pending review requests on batch formation and marker ingestion.
  - `companion/cli.py`: Update `companion observe live-status` with request queue and bridge metrics.
  - `.hermes/skills/poe2-live-observation/SKILL.md`: Project-local skill guiding actual Hermes live observation.
- **Dependencies**: Uses existing project dependencies (`pydantic`, `mss`, standard library `queue`, `threading`, `time`, `os`, `pathlib`). Zero new runtime packages, OCR libraries, or external AI provider client dependencies.
- **Compliance & Safety**: Fully passive; zero game inputs; strictly local gitignored storage; no credential or private chat capture; fail-closed anomaly sampling; non-blocking bounded drain; crash-consistent replay deduplication; complete decoupling of AI provider availability from runtime stability.
