# Proposal: Continuous Foreground Runtime for PoE2 Companion

## Why

While individual sensing, reconciliation, objective derivation, and notification components are verified and operational as batch operations, the user currently must manually invoke disparate CLI commands to poll state or evaluate objectives. A single, passive, continuous foreground runtime loop is required so players can launch the companion once during a Path of Exile 2 gaming session and receive automatic, change-driven objective tracking and safe-zone notifications without manual intervention or game-altering background daemons.

## What Changes

- Add a continuous foreground runtime orchestrator (`companion.runtime.orchestrator` / `companion runtime start`) executing a deterministic pipeline: process presence monitoring, bounded incremental `Client.txt` tailing, observation normalization with stable stream generation and provenance, single-writer `CharacterState` reconciliation via canonical public store API, change-driven objective derivation, safe-zone notification delivery, and persistent journey/session checkpointing.
- Add an explicit crash-consistency model based on at-least-once log consumption with idempotent state reconciliation and durable checkpoint sequencing: observations carry stable source identities incorporating a durable stream epoch (`file_fingerprint:epoch_N:start_offset:end_offset:event_type`) preventing identity collisions after file truncation and suppressing duplicate journey entries on replay.
- Implement durable idempotency for non-idempotent state mutations (specifically `death_count`) by persisting a durable per-counted-effect source watermark (`last_counted_death_stream_id` and `last_counted_death_end_offset` in `death_count.evidence_refs`) atomically with the counter within canonical `CharacterState`, replacing magic fixed-size ID windows and guaranteeing that replayed records across process crashes cannot cause counter drift or double-counting regardless of batch size.
- Add a lightweight `Client.txt` file identity fingerprint (combining creation metadata and initial header bytes) and a durable `stream_epoch` stored in checkpoints to reliably distinguish normal append growth, in-place file truncation, and rotated/replaced log files (even when a replacement file is larger than the saved offset or prefix bytes match).
- Define explicit dirty-on-start checkpoint termination semantics: before processing any log observation, runtime startup durably marks `clean_shutdown = False`; only after bounded final drain, durable state, and final checkpoint offset are persisted during graceful shutdown does the runtime mark `clean_shutdown = True` and `clean_shutdown_at`. Crash restart resumes from checkpoint offset with at-least-once replay, while clean graceful restart while the game is running establishes an honest new live boundary at current EOF to avoid replaying offline backlog as present-tense alerts.
- Add explicit startup baseline tail policies: when companion starts before the game, an idle baseline EOF is captured so launch-time log entries are not skipped; when companion starts while the game is already running after clean shutdown, current EOF establishes the starting boundary with honest reporting that pre-startup session logs are unobserved.
- Add a deterministic historical `--backfill` to live transition boundary: captures `startup_backfill_end_offset` at launch, ingests historical logs up to that offset with notifications suppressed and original timestamps preserved, and smoothly transitions to live alerting mode for records appended past that boundary.
- Enforce canonical single-writer ownership via OS-backed lifetime lock: the continuous runtime acquires and holds an exclusive OS file lock (`runtime/writer_lease.lock`, reusing the project's Windows `StateLock` mechanism) for its entire lifetime as the sole ownership authority. Atomic OS lock acquisition eliminates check-then-create races between racing runtimes; a competing runtime or mutating CLI (`companion session tail`, `companion state init`) immediately fails lock acquisition and refuses execution with `RUNTIME_WRITER_ACTIVE`. Diagnostic metadata (`runtime/writer_lease.json`) records PID, run_id, and heartbeat for inspection but never independently grants ownership. On runtime crash, the OS releases the lock automatically, enabling subsequent owners to acquire writer ownership even if stale metadata contains old or reused PIDs, while a held OS lock can never be stolen merely because a heartbeat appears stale. Mutating commands participate in this atomic lock contract before read-modify-write; read-only commands remain allowed; and graceful shutdown releases the OS writer lock strictly after final durable state and checkpoint persistence.
- Preserve canonical M1 state persistence: the runtime calls the public `CharacterStateStore.save_character(state)` API rather than private persistence methods.
- Add batch coalescing and exit log draining: multi-event poll batches consolidate state changes and trigger at most one objective derivation cycle, while game process termination triggers a bounded final `Client.txt` drain before session recap and checkpoint finalization.
- Add bounded safe-zone notification queue management enforcing semantic deduplication keyed by objective identity, preventing repetitive pending advisories from accumulating without bound while characters remain in combat zones.
- Add session lifecycle management tracking game state transitions (`IDLE` -> `GAME_RUNNING` -> `SESSION_ACTIVE` -> `GAME_EXITED`) with clean session opening, checkpoint flushing, and graceful shutdown on `Ctrl+C` (SIGINT/SIGTERM).
- Add structured console observability providing human-readable, low-noise event feeds (`[SESSION]`, `[ZONE]`, `[LEVEL]`, `[OBJECTIVE]`, `[NOTIFY]`) with optional verbose/debug output.
- Add a lightweight atomic heartbeat status file (`runtime/runtime_status.json`) enabling `companion runtime status` cross-process inspection with PID liveness and staleness checks without sockets, HTTP servers, or background services.
- Add isolated error boundaries ensuring malformed log lines, temporary file locking, or notification sink failures do not crash the loop or corrupt `CharacterState` persistence, while strictly enforcing read-only access to game log files.

## Capabilities

### New Capabilities
- `continuous-runtime`: Lightweight continuous foreground loop coordinating process detection, incremental log streaming with stable stream generation and provenance, idempotent state reconciliation, change-driven objective derivation, safe-zone notification routing, bounded exit draining, and crash-consistent checkpoint recovery for an active PoE2 session without background daemons, network services, or game input.

### Modified Capabilities
*(None; existing specifications for `session-monitoring`, `client-log-streaming`, `state-reconciliation`, `objective-engine`, `notification-system`, `companion-cli`, and `no-input-compliance` remain intact and are composed without altering their component contracts).*

## Impact

- **Affected Code**: Adds `companion/runtime/` package (orchestrator, lifecycle, checkpoint, fingerprint, status, change detector) and adds `runtime` subcommands (`start`, `status`) to `companion/cli.py` and `companion/__main__.py`. Composes existing modules (`sensing`, `state`, `objectives`, `notifications`).
- **Dependencies**: Zero new third-party dependencies. Uses Python standard library (`argparse`, `signal`, `time`, `pathlib`, `json`, `hashlib`, `os`).
- **Compliance**: Preserves 100% compliance with `no-input-guard` (no hooks, no `SendInput`, no keyboard/mouse simulation, no memory reading, no game injection).
- **APIs & Game Boundary**: Completely passive and read-only. Game log access is strictly read-only binary (`"rb"`). GGG OAuth/API remains externally blocked and decoupled. Screen capture remains strictly explicit/opt-in (no background OCR/CV).
