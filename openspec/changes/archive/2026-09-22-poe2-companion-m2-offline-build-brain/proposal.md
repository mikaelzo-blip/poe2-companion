# Proposal: M2 Offline Build Brain

## Why

Following the completion and archival of M0 (Source Validation & Ingestion) and M1 (Character State Foundation), the companion needs an offline, deterministic domain engine to evaluate player character state against target build reference data. Without this capability, the system cannot determine which build progression phase applies, which target variant is active, what build content is currently level-eligible, or what factual differences exist between observed player facts and target requirements. 

Building M2 establishes this core "Build Brain" in pure offline Python before any transition rules (M3) or objective evaluation algorithms (M4) are introduced.

## What Changes

- **Build Eligibility Engine & Boundary Defense**: Introduces deterministic evaluation of normalized build intervals (`level_interval`) against player level, returning explicit semantic states (`ACTIVE`, `FUTURE`, `EXPIRED`, `UNKNOWN`). Preserves single-uint interval uncertainty without guessing semantics, and strictly defends against invalid character levels (level <= 0 or level > 100) via boundary validation failure rather than silent mapping.
- **Progression Phase Resolver**: Deterministically resolves character progression phase across six distinct stages (`LEVELING_1_14`, `LEVELING_15_32`, `LEVELING_33_51`, `POST_52_53_68`, `LEVELING_69_84_FALLBACK`, `HIGH_END`). Explicitly binds `LEVELING_69_84_FALLBACK` (levels 69–84) to the `lvl 53-68` target snapshot as a deterministic companion fallback policy with recorded provenance due to the lack of a dedicated upstream snapshot. Excludes persistent Level-52 transition state machine logic (which remains strictly scoped to M3).
- **Target Variant Resolver & Explicit Resolver Input**: Resolves high-end variants (`LVL85`, `ENDGAME`, `MAGEBLOOD`, `DOT_CAP`) non-monotonically (`Mageblood ⊄ Endgame`, `DoT Cap ⊄ Mageblood`). Defines an explicit evaluator input contract (`BuildBrainInput` accepting `character_state`, `observation_coverage: PlayerObservationCoverage`, and `selected_target_variant: TargetVariant | None = None`). When `progression_phase = HIGH_END` and `selected_target_variant is None`, returns a structured unresolved result (`TargetVariantResolution` with `variant: null`, `status: UNRESOLVED`, `reason: NO_EXPLICIT_HIGH_END_VARIANT`) rather than assuming an implicit default like `LVL85`. Persistence, prompting, and UX for variant selection remain strictly external to M2. Item possession never silently resolves or mutates the variant. Outside high-end, returns `NONE`.
- **Target Evidence, Precedence & Source Availability**: Consumes target/reference truth under Blueprint v2 precedence and explicitly surfaces source availability states (`USABLE`, `PENDING_VERIFICATION`, `UNAVAILABLE`). Outputs structured `CONFLICTING_EVIDENCE` records when sources materially disagree without silent tie-breaking. Reserves the PoB2 precedence slot without fabricating unverified facts or implementing a PoB parser in M2.
- **Passive Logical Identity & Target Canonicalization**: Compares passives using the compound logical key `(passive_id, weapon_set_context)` across contexts (`DEFAULT_OR_SHARED`, `SPECIALISATION_1`, `SPECIALISATION_2`, `UNKNOWN_RESERVED`). Canonicalizes duplicate raw source occurrences into single allocation requirements while preserving all raw `source_occurrences`, source row indices, and interval provenance for audit. Checks duplicate occurrence metadata for material disagreements, surfacing conflicts rather than silently picking an arbitrary row.
- **Semantic Skill-Group Identity & Meta-Gem Representation**: Represents target skills as structured skill groups whose logical identity derives from stable semantic structure (primary/meta-gem identity, parent/meta context, and active child context) rather than source group index, which is retained solely as audit provenance. Reordering source group indices between snapshots does not alter logical interpretation. Explicitly distinguishes standalone active gems (e.g. standalone `Tornado`) from child gems inside meta-gem setups (e.g. `Tornado` socketed in `Cast on Dodge`), evaluates gem level eligibility (`Cast on Dodge [58, 100]` is `FUTURE` at level 52, never `MISSING`), and does not infer weapon-set assignments absent from `.build` files.
- **Centralized Observation Coverage & MISSING Invariant**: Distinguishes evidence quality from observation coverage via explicit input model `PlayerObservationCoverage` tracking scoped `ObservationCoverage` (`COMPLETE`, `PARTIAL`, `UNKNOWN`) for passives, skills, and per-slot equipment. A delta item may evaluate to `MISSING` only when all five conditions hold: active target, fresh observation, sufficient evidence quality, COMPLETE scoped coverage, and confirmed entity absence. If coverage is `PARTIAL`, returns `UNKNOWN` with `reason: PARTIAL_PLAYER_OBSERVATION`; if coverage is not supplied or unknown, returns `UNKNOWN` with `reason: OBSERVATION_COVERAGE_UNKNOWN`. Completeness is never inferred from `VerificationState.VERIFIED`. Applied consistently across passives, skills, and equipment via a single shared policy helper.
- **Conservative Equipment Delta**: Compares equipment factually using existing `CharacterState` slot identifiers, weapon-set context where applicable, known structured observations (`unique_name`, base type), and slot-scoped observation coverage without introducing gear score, upgrade scoring, affix optimization, economy logic, or OCR.
- **Structured M2 Output Contract**: Emits typed, structured results (`BuildDeltaResult`) consumable by downstream M3 and M4 milestones without human prose, transition state machine evaluation, objective ranking, or notifications.

## Capabilities

### New Capabilities
- `build-eligibility-progression`: Deterministic evaluation of item/skill/passive level eligibility (`ACTIVE`, `FUTURE`, `EXPIRED`, `UNKNOWN`), strict validation against invalid character levels (<= 0 or > 100), and character progression phase resolution across leveling and high-end boundaries (explicitly specifying `lvl 53-68` fallback for levels 69–84 with recorded provenance).
- `target-resolution`: Deterministic selection of target build snapshots, explicit `BuildBrainInput` input contract, non-monotonic high-end variant resolution (`LVL85`, `ENDGAME`, `MAGEBLOOD`, `DOT_CAP`, `NONE`) returning structured `TargetVariantResolution` (`UNRESOLVED` with `NO_EXPLICIT_HIGH_END_VARIANT` when unselected at high-end), source availability tracking (`USABLE`, `PENDING_VERIFICATION`, `UNAVAILABLE`), and structured handling of source data conflicts without fabricating PoB2 data.
- `build-delta`: Deterministic comparison between observed `CharacterState` facts and resolved target build requirements across passives (compound logical identity with hardened canonicalization), skills (semantic skill-group identity independent of index reordering, distinguishing standalone vs meta-gem setups), and conservative equipment, governed by a shared UNKNOWN/STALE/MISSING policy helper enforcing scoped `ObservationCoverage`.

### Modified Capabilities
*(None. Canonical specs from M0/M1 for `character-state`, `no-input-compliance`, and `source-ingestion` remain authoritative and unmodified.)*

## Impact

- **New Modules**: Adds lightweight, cohesive domain modules under `companion/build/` (e.g. `eligibility.py`, `progression.py`, `variants.py`, `passives.py`, `skills.py`, `equipment.py`, `conflicts.py`, `policy.py`, `delta.py`).
- **Dependencies**: Uses existing project dependencies (`pydantic`, `pyyaml`). No external network, database, GUI, or rule-engine dependencies added.
- **M0/M1 Compatibility**: Consumes `NormalizedBuild`, `NormalizedPassiveEntry`, `NormalizedSkillEntry`, `LevelInterval`, and `CharacterState v2` without altering their schemas or behavior.
- **Downstream Contracts**: Prepares the foundational delta and eligibility contracts consumed by M3 (Level-52 transition rules) and M4 (objective ranking engine).
