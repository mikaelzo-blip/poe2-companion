# Proposal: PoE2 Equipment Intelligence & Gear Brain

## Why

Deciding whether an item is an upgrade in Path of Exile 2 cannot be solved by a static item score (e.g. "82/100") or a generic passive-tree planner. In PoE2, gear value is strictly contextual: a ring providing +100 Life and offense may look attractive in isolation, but equipping it could remove 40% Lightning Resistance from the current ring, dropping the character below resistance cap and causing lethal vulnerability. Furthermore, build mechanics can make superficially good modifiers actively destructive. For example, in Fubgun's Level-52+ post-swap Flameblast / Oil Grenade build, the verified rule is: *"You cannot have flat fire damage or extra fire damage anywhere on your gear (the only exception is your staff)."* The core mechanical risk is that added or extra Fire damage applying to Oil Grenade (attacks) causes Oil Grenade itself to trigger an inferior, weak ignite that blocks the massive ignite from the Flameblast staff. A simplistic rule checking only weapon slots fails by missing harmful shared rings or gloves while falsely rejecting the allowed Flameblast staff.

PoE2 Companion requires a dedicated, deterministic Equipment Intelligence ("Gear Brain") subsystem. Rather than treating gem setups or the passive tree as primary, this system focuses squarely on equipped items, candidate items copied from the stash or inventory, and whole-character stat baselines. It evaluates character defensive deficits, dynamic marginal stat values, attribute requirements, slot opportunity costs, dual-weapon-set context, and stage-aware build-breaking rules to produce transparent, actionable verdicts: `EQUIP_NOW`, `CONDITIONAL_UPGRADE`, `KEEP_FOR_LATER`, `REJECT`, or `INSUFFICIENT_DATA`.

Critically, official Path of Exile 2 API capabilities do not expose complete character-sheet stats (Life, Resistances, Armour, Evasion, Energy Shield, Attributes, Movement Speed) and do not support unequipped inventory/backpack discovery or private account stashes. Equipment Intelligence must maintain absolute integrity: never fabricating unknown stats as zero, providing an explicit offline manual loadout ingestion workflow via clipboard (`companion gear loadout set-clipboard`), tracking loadout provenance and flagging API/manual conflicts (`CONFLICTING`), explicitly modeling shared gear and dual weapon sets (Flameblast set 1 staff vs Oil Grenade set 2 crossbow), supporting an expanded manual character stat baseline with optional defenses and max resistances, strictly preventing double-counting between character-sheet totals and item contributions, supporting partial swap projections when baselines are unobserved, and operating fully without official API credentials.

Finally, to guarantee implementation safety and operational correctness before code is written, three critical invariants must be established:
1. **Loadout-to-Baseline Revision Anchoring, Initial Setup, and Resistance Rebase Policy**: A character baseline represents facts observed while a specific equipment loadout was active. The system strictly distinguishes initial loadout capture from post-setup equipment mutation. In the initial setup workflow, the user captures all known currently equipped items (shared slots, weapon set 1, weapon set 2) into a draft loadout, optionally partial with unobserved slots explicitly retained as `UNKNOWN`. Finalizing the loadout (`companion gear loadout finalize`) establishes `loadout_id` and initial stable `revision = 1`. The character baseline (`companion gear baseline set`) is captured only after loadout finalization and anchored directly to revision 1, ensuring character-sheet numbers and stored gear describe the same equipment state. Post-setup mutations (`promote-candidate`, explicit replacement of established slots) increment `loadout.revision` and trigger baseline reconciliation.
Crucially, the system SHALL NOT perform additive resistance rebasing directly against a capped effective resistance value. It explicitly distinguishes `raw_uncapped_resistance`, `effective_resistance`, `max_resistance`, and `overcap_buffer`. Safe deterministic resistance rebase is permitted only when enough information exists to reconstruct the raw state (raw uncapped value known, or effective + verified overcap buffer). Then `new_raw = old_raw - displaced_item + candidate` and `new_effective = min(new_raw, verified_max_resistance)`. If raw state cannot be proven, the system reports the known item delta, but marks the new absolute effective resistance as `UNKNOWN` / `STALE`. Complex non-linear defenses (Armour, Evasion, Energy Shield) are likewise marked `STALE` / `UNKNOWN`. A fresh manual baseline re-snapshot workflow (`companion gear baseline set` / refresh) allows re-anchoring directly to the current revision as `VERIFIED`/`MANUAL`, replacing long chains of derived baseline values. Candidate inspection and recommendations remain strictly read-only and never mutate loadout revisions.
2. **Generalized Slot Conflict Topology & Multi-Slot Weapon Displacement**: Rather than encoding a universal assumption that two-handed items conflict with every off-hand accessory or deriving weapon occupancy from build guides alone, normalized base metadata exposes actual slot-conflict topology (`occupied_slots`, `conflicting_slots`, `allowed_companion_slots`) grounded in verified PoE2 game-item rules. In Path of Exile 2, Staves and Crossbows are both two-handed weapon classes that occupy both weapon slots (`main_hand` and `off_hand`) and conflict with both weapon slots in their respective weapon set. Quivers can only be equipped while wielding a Bow, never with a crossbow. Therefore, for the verified Fubgun 0.5.5 profile, the Flameblast staff in weapon set 1 occupies both weapon hand slots, and the Oil Grenade crossbow in weapon set 2 occupies both weapon hand slots with zero off-hand quiver contribution. Generic occupancy metadata preserves future support for other weapon classes (such as bows permitting quivers) without hardcoding every two-handed weapon to identical exception behavior. UNKNOWN topology remains UNKNOWN, blocking confident full projection. When evaluating a candidate weapon, the projected swap removes and displaces all conflicting items in that set while completely isolating the opposing weapon set. Multi-slot contribution and requirement cascades subtract stats from all displaced items without retaining or subtracting a fictional quiver.
3. **High-Risk Unknown Build-Breaker Gating & Deterministic Verdict Precedence**: Build-relevant modifiers follow a tri-state certainty model (`VERIFIED_SAFE`, `VERIFIED_BUILD_BREAKER`, `UNKNOWN_APPLICABILITY`). When a candidate contains a modifier that plausibly activates a verified `HARD_REJECT` mechanic (such as an unverified fire damage affix applying to Oil Grenade attacks) but its applicability cannot be proven, the engine must never emit a confident `EQUIP_NOW` verdict. It must conservatively emit `INSUFFICIENT_DATA` or `CONDITIONAL_UPGRADE` with explicit `HIGH_RISK` warnings. The final decision must follow a strict, non-scalar precedence hierarchy (`VERIFIED_BUILD_BREAKER` -> `CRITICAL REQUIREMENT FAILURE` -> `UNKNOWN POTENTIAL BUILD-BREAKER` -> `NEW CRITICAL CHARACTER DEFICIENCY` -> Normal gear improvement).

## What Changes

- **Distinguish Initial Setup from Post-Setup Equipment Mutation**: The initial setup workflow allows the user to describe equipment that was ALREADY equipped when the character-sheet baseline was observed. Capturing items via `companion gear loadout set-clipboard --slot <slot>` populates a setup/loadout draft without simulating gear swaps or incrementing revisions. Finalization (`companion gear loadout finalize`) establishes `loadout_id` and initial stable `revision = 1`. Only AFTER finalization is the character baseline captured (`companion gear baseline set ...`), anchoring to revision 1.
- **Partial Initial Loadout Support**: Does not require every slot to be known. Unobserved slots remain `UNKNOWN`. Finalization records known slots, unknown slots, and verification state. Gear Brain lowers confidence when a candidate projection depends on an unknown displaced item (e.g. current boots `UNKNOWN`, candidate boots known -> describes candidate properties, but cannot claim exact net boots delta).
- **Version / Anchor Character Baseline to Equipped Loadout**: Persists an explicit, auditable relationship between `CharacterStatBaseline` and `EquippedLoadout`. `EquippedLoadout` retains `loadout_id`, a monotonic integer `revision`, and `updated_at`. `CharacterStatBaseline` stores `baseline_id`, `anchored_loadout_revision`, `observed_at`, and provenanced facts. A baseline never silently remains authoritative after the stored loadout revision changes.
- **Post-Setup Loadout Mutation & Safe Baseline Reconciliation**: Commands representing real equipment changes after finalization (`companion gear loadout promote-candidate`, explicit replacement of an established current slot) increment `loadout.revision` and trigger baseline reconciliation:
  - *Safe Deterministic Resistance Rebase Policy (Raw vs Effective)*: The system explicitly distinguishes `raw_uncapped_resistance`, `effective_resistance`, `max_resistance`, and `overcap_buffer`. The system strictly refuses to perform additive item rebasing directly against a capped effective value (e.g. 75% cap with 115% raw losing 40% Res drops raw to 85% and keeps effective at 75%, not 45%). Safe deterministic rebase is allowed only when raw state is known or reconstructible from effective + overcap buffer: `new_raw = old_raw - displaced + candidate; new_effective = min(new_raw, current_max_resistance)`. If raw state cannot be proven, the engine reports the known item resistance delta but marks new absolute effective resistance as `UNKNOWN` / `STALE`.
  - *Safe Deterministic Attribute Rebase*: For linear attributes (Strength, Dexterity, Intelligence), computes `new_baseline = old_verified_baseline - old_item_contrib + new_item_contrib` (`source = DERIVED_CALCULATION`).
  - *Mark Complex Defenses Stale / Unknown*: For complex, non-linear stats subject to global multipliers or passives (total Armour, Evasion, Energy Shield), the engine marks the total baseline fact as `STALE` / `UNKNOWN` rather than fabricating an unsubstantiated new total.
- **Explicit Re-Snapshot / Rebase Workflow**: Allows the user to refresh the baseline after several equipment changes via `companion gear baseline set ...` or `baseline refresh`. The fresh manual baseline becomes `VERIFIED` / `MANUAL` and anchors directly to the current loadout revision, replacing long chains of derived baseline values with a fresh authoritative snapshot.
- **Baseline Consistency Gate**: Before evaluating candidate items, `EquipmentIntelligenceEngine` verifies that `baseline.anchored_loadout_revision` matches `current_loadout.revision`. If mismatched and unreconciled, affected facts are marked `STALE` / `UNKNOWN` and cannot serve as authoritative current totals. Known item-level deltas continue to be computed and surfaced honestly.
- **Strict Read-Only Candidate Recommendations**: Candidate inspection (`companion gear inspect-clipboard`, `companion gear evaluate`, `compare`, `recommendation`) produces recommendations strictly read-only. Generating an `EQUIP_NOW` recommendation never mutates stored loadout state or increments the loadout revision. Only an explicit user confirmation command (`companion gear loadout promote-candidate`) mutates equipped loadout.
- **Generalized Slot Conflict Topology & Handedness Modeling**: Extends item models with explicit slot-conflict topology (`occupied_slots`, `conflicting_slots`, `allowed_companion_slots`) derived from verified PoE2 game-item metadata rather than generic guide text. Under PoE2 rules, Staves and Crossbows are both two-handed weapon classes occupying and conflicting with both weapon hand slots (`main_hand` and `off_hand`) in their respective sets. Quivers can only be equipped while wielding a Bow, not with a crossbow; bows may have their own verified Bow + Quiver rule in metadata, but quivers are not part of the Fubgun V1 loadout. For the Fubgun profile, both Set 1 (Flameblast staff) and Set 2 (Oil Grenade crossbow) occupy both weapon hand slots with no quiver contribution. Unrecognized topology remains strictly `UNKNOWN_TOPOLOGY`, blocking confident full projection.
- **Two-Handed Weapon Projection & Opposing Set Isolation**: When a candidate weapon targets a weapon set, the projection engine removes all verified conflicting slots in that same set. The opposing weapon set remains completely untouched. Replacing a two-handed weapon with a one-handed weapon leaves the off-hand slot empty/unknown without fabricating phantom gear.
- **Occupancy-Aware Multi-Slot Contribution & Requirement Cascades**: When replacing a multi-slot configuration (or equipping a multi-slot item), the engine subtracts contributions from ALL displaced items. Defenses, Life, resistances, and attributes are recomputed across the displaced topology, preventing phantom off-hand contributions and ensuring requirement cascades catch lost off-hand attributes.
- **High-Risk Unknown Build-Breaker Gate**: Invariant enforcing that if a candidate contains a modifier with unproven applicability that could plausibly activate a verified build-breaking mechanic (e.g. newly encountered Fire damage affix that might apply to Oil Grenade), Equipment Intelligence MUST NOT emit a confident `EQUIP_NOW` verdict. It emits `INSUFFICIENT_DATA` or `CONDITIONAL_UPGRADE` with an explicit `HIGH_RISK` warning, refusing to fabricate rejections or ignore risks.
- **Build-Breaker Certainty Model**: Distinguishes `VERIFIED_SAFE` (e.g. Fire Resistance, % increased Fire Damage), `VERIFIED_BUILD_BREAKER` (e.g. post-swap shared ring with added fire to attacks -> `HARD_REJECT`), and `UNKNOWN_APPLICABILITY` (unverified fire modifiers blocking confident `EQUIP_NOW`).
- **Deterministic Non-Scalar Verdict Precedence**: Replaces any potential score reduction with an explicit evaluation hierarchy:
  1. `VERIFIED_BUILD_BREAKER` -> `REJECT`
  2. `CRITICAL REQUIREMENT FAILURE` -> `REJECT` or `CONDITIONAL_UPGRADE` (based on attribute recoverability)
  3. `UNKNOWN POTENTIAL BUILD-BREAKER` -> blocks `EQUIP_NOW`, emitting `INSUFFICIENT_DATA` or `CONDITIONAL_UPGRADE`
  4. `NEW CRITICAL CHARACTER DEFICIENCY` -> `CONDITIONAL_UPGRADE` or `REJECT`
  5. Normal Gear Improvement -> `EQUIP_NOW`, `CONDITIONAL_UPGRADE`, or `KEEP_FOR_LATER`.
- **Precise Fubgun Post-Swap Fire-Damage Rule**: Corrects the build-breaker evaluation from a crude weapon-slot check to the verified Fubgun 0.5.5 mechanical rule: flat fire damage or extra fire damage anywhere on gear is forbidden if it applies to Oil Grenade, with the Flameblast staff as the sole verified exception. Evaluates normalized modifier family, item slot, shared vs weapon-set placement, target weapon set, whether the modifier is active/applicable in Oil Grenade attack context, and progression stage. Shared rings/gloves with added Fire to attacks and Oil Grenade crossbows with added/extra Fire are `HARD_REJECT`; Flameblast-specific staff fire modifiers under weapon set 1 are preserved; non-harmful modifiers (`FIRE_RESISTANCE`, `% increased Fire Damage`) are not rejected; and unverified fire modifier applicability evaluates to `UNKNOWN` / `HIGH_RISK` without fabricated rejections.
- **Offline Current-Loadout Ingestion via Clipboard & Finalization**: Defines a concrete, passive manual loadout ingestion workflow for V1: the user hovers an equipped item in-game, presses `Ctrl+C`, and runs `companion gear loadout set-clipboard --slot <slot>` (e.g. `boots`, `ring1`, `ring2`, `weapon-set-1-main`, `weapon-set-2-main`). These populate a draft loadout. The user then runs `companion gear loadout finalize` to establish `loadout_id` and initial stable `revision = 1`. Unobserved slots remain `UNKNOWN`. Also provides `companion gear loadout show` and `companion gear loadout clear <slot>`. No game-client automation or keystroke injection is used.
- **Loadout Storage & Provenance Tracking**: Persists the manually established current loadout locally in `EquippedLoadout`. Each slot retains the normalized `ItemCandidate`, `source` (`CLIPBOARD_ITEM_TEXT`, `GGG_OFFICIAL_API`, `MANUAL`), `observed_at`, `verification`, and `evidence_ref`. Contradictory API and manual states are never silently merged; conflicting states are marked `verification: CONFLICTING` and surfaced to the user.
- **Dual Weapon-Set Manual Loadout Modeling & Generalized Conflict Topology**: First-class support for `SHARED EQUIPMENT` (Helm, Body Armour, Gloves, Boots, Amulet, Ring 1, Ring 2, Belt), `WEAPON_SET_1` (Flameblast two-handed staff occupying both hand slots), and `WEAPON_SET_2` (Oil Grenade two-handed crossbow occupying both hand slots). Slot conflict topology is declared in normalized item metadata (`occupied_slots`, `conflicting_slots`, `allowed_companion_slots`) grounded in verified PoE2 game-item rules rather than inferred from generic handedness assumptions.
- **Expanded Authoritative Character Stat Baseline with Raw vs Effective Distinctions**: Extends `CharacterStatBaseline` to store Life, Fire/Cold/Lightning/Chaos resistances explicitly distinguishing `raw_uncapped_resistance`, `effective_resistance`, `max_resistance`, and `overcap_buffer`, alongside Armour, Evasion, Energy Shield, Strength, Dexterity, Intelligence, Movement Speed, and current maximum resistances via `companion gear baseline set`. Omitted fields remain `UNKNOWN` rather than zero, maintaining strict provenance.
- **Character Baseline vs Item Contribution Double-Count Protection**: Explicitly separates character-sheet baseline totals (e.g. Armour = 4200) from loadout-derived item contributions (e.g. body armour Armour = 850). The engine never adds current item defense back into reported total baseline defense. Projected swap values use `projected = current_total - old_item_contribution + candidate_contribution` only where contribution semantics are valid; when global scaling interactions make absolute projection unsafe, the engine reports known local deltas and flags uncertainty.
- **Candidate Evaluation vs Loadout Mutation Separation**: Candidate inspection (`companion gear inspect-clipboard`, `companion gear evaluate`, `compare`, `recommendation`) evaluates swaps read-only. Generating an `EQUIP_NOW` recommendation never mutates the stored loadout. A dedicated command (`companion gear loadout promote-candidate`) allows the user to explicitly promote an equipped item into their stored loadout.
- **Partial Projection Semantics with Partial Loadout Awareness**: Decouples deterministic `KNOWN DELTA` from `PROJECTED ABSOLUTE VALUE`. When baseline stats (e.g. current Lightning Resistance) are `UNKNOWN`, the engine deterministically reports the equipment delta (e.g. `-28% Lightning Resistance`) while refusing to fabricate absolute values (e.g. `75% -> 47%`), yielding `INSUFFICIENT_DATA` or `CONDITIONAL_UPGRADE` with identified risk. When an equipped slot is `UNKNOWN` (partial loadout), the engine describes candidate properties but refuses to assert an exact net slot delta.
- **Local vs Global Modifier Semantics**: Classifies parsed modifiers into typed scopes (`LOCAL_ITEM_STAT`, `GLOBAL_CHARACTER_STAT`, `REQUIREMENT`, `BUILD_MECHANIC`, `CONDITIONAL`, `UNKNOWN_SCOPE`). Prevents double-counting local defense increases (e.g. local % increased Armour on Body Armour is not added again globally when displayed Armour already incorporates it).
- **Deterministic Item Contribution Model**: Routes all projection through an `ItemContribution` layer exposing character-relevant deltas rather than summing raw parsed numbers.
- **Dynamic Resistance Limit & Raw Overcap Buffer Modeling**: Replaces hardcoded 75% assumptions with a dynamic model distinguishing `raw_uncapped_resistance`, `effective_resistance`, `max_resistance`, and `overcap_buffer`. Refuses to invent campaign/progression resistance penalty formulas unless explicitly verified.
- **Requirement Cascade Validation**: Evaluates whole-loadout dependency cascades when gear swaps alter Strength, Dexterity, or Intelligence, verifying that removing an attribute item does not silently break requirements on other equipped gear or build-critical gems.
- **Official API Capability Gating & OAuth 2.1**: Honestly marks unequipped inventory and account stashes as `UNAVAILABLE_BY_CURRENT_OFFICIAL_API` for PoE2. Clarifies OAuth 2.1 public client requirements with PKCE while documenting GGG's current registration freeze and feature-gating official synchronization (`API_AVAILABLE`, `AUTH_CONFIGURED`, `AUTH_UNAVAILABLE`).
- **Complete Offline V1 Workflow**: Guarantees core Equipment Intelligence functions without official API credentials via manual draft loadout capture, loadout finalization, manual baseline setup, candidate evaluation via clipboard, and explicit loadout promotion.
- **Strict Read-Only Gameplay Safety**: Strictly complies with anti-automation guidelines: zero simulated keypresses (`SendInput`), zero mouse control (`pyautogui`/`pynput`), zero memory reading or injection, and zero automated equip or trade actions.

## Capabilities

### New Capabilities

- `equipment-intelligence`: Deterministic equipment evaluation, authoritative character stat baseline with UNKNOWN handling, raw vs effective resistance distinction, safe raw resistance rebase policy, baseline-to-loadout monotonic revision anchoring, initial loadout draft capture vs finalization (`revision = 1`), partial loadout support, post-equip safe baseline reconciliation (`DERIVED_CALCULATION` for additive raw stats vs `STALE` for unproven defenses), baseline consistency gating, fresh baseline re-snapshot workflow, generalized slot-conflict topology modeling, two-handed weapon projection displacing conflicting slots, occupancy-aware multi-slot contribution removal and requirement cascades, build-breaker certainty tri-state model (`VERIFIED_SAFE`, `VERIFIED_BUILD_BREAKER`, `UNKNOWN_APPLICABILITY`), high-risk unknown build-breaker gating blocking confident `EQUIP_NOW`, deterministic verdict precedence hierarchy, partial swap projection, dual weapon-set loadout modeling, offline manual loadout ingestion via clipboard, loadout provenance and conflict detection, local vs global modifier distinction, ItemContribution layer, dynamic resistance targets, requirement cascade validation, exact Fubgun build-breaker predicates with staff exception, recommendation-to-loadout mutation separation, candidate-to-loadout promotion, manual baseline fallback, and API capability gating.

### Modified Capabilities

- None. Existing capabilities (`gear-analysis` for legacy visual tooltip audits, `character-state` for runtime persistence) remain untouched.

## Impact

- **New Subsystem**: `companion.equipment` containing normalized item models, clipboard parser, modifier normalizer, baseline store, loadout manager, projection engine, deficiency analyzer, build rules engine, and recommendation formatter.
- **CLI Commands**: Introduces `companion gear baseline set`, `companion gear baseline refresh`, `companion gear baseline show`, `companion gear loadout set-clipboard`, `companion gear loadout finalize`, `companion gear loadout show`, `companion gear loadout clear`, `companion gear loadout promote-candidate`, `companion gear inspect-clipboard`, and `companion gear evaluate` subcommands.
- **Official API Integration**: Gated under OAuth 2.1 client checks, mapping official equipped items when configured without depending on unavailable inventory/stash endpoints.
- **Dependencies**: No new external dependencies beyond existing project dependencies (`pydantic>=2.0`, `pyyaml>=6.0`, standard library `urllib`, `dataclasses`, `re`, `json`).
