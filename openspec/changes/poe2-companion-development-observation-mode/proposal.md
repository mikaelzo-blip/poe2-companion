# Proposal: Development Observation Mode

## Why

Developing and tuning the Path of Exile 2 Companion requires real gameplay evidence to identify parser gaps (such as unhandled `Client.txt` formats like DEF-01), detect noisy objective churn, assess notification utility, and understand real-world state transitions. However, testing during live play must never distract the player, violate game automation rules, or perturb the continuous runtime.

Currently, diagnosing runtime edge cases requires manual log inspection or post-hoc log reconstruction. Development Observation Mode introduces a passive, privacy-safe, read-only observation tap that attaches to the existing continuous runtime. It records structured session telemetry, state deltas, objective decision traces, notification outcomes, unknown log anomaly signatures, manual player markers, and optional event-triggered screenshots. Crucially, the observer is strictly subordinate to the continuous runtime: it operates through a bounded asynchronous pipeline that cannot block or crash runtime correctness, employs fail-closed privacy filters, guarantees atomic marker coordination without shared queue corruption, maintains recoverable session manifests across crashes, executes an orderly bounded shutdown drain without indefinite blocking, handles worker degradation gracefully, and enforces deterministic global retention that protects newly finalized sessions.

Furthermore, development observation cleanly decouples local live analysis from AI provider availability through a crash-consistent two-plane architecture:
1. **Local Live Analysis Data Plane**: A deterministic, read-only local process (`companion observe analyze-live`) operates under an at-least-once input and idempotent derived output contract. It continuously reads new structured evidence, maintains stream continuity across rotated segments, updates deterministic factual signals with stable identities (`local_signals.jsonl`), tracks persistent UNKNOWNs and churn patterns, and advances its durable reader cursor (`reader_state.json`) strictly after successful output persistence, recovering independently of external AI availability.
2. **Hermes AI Review Plane**: When Hermes is active, it consumes unreviewed evidence starting from its durable review cursor (`hermes_review_cursor.json`), inspects raw local evidence safely when necessary, performs causal correlation on high-priority player markers, evolves structured findings via stable identities (`hermes_findings.jsonl`), updates its active heartbeat status (`hermes_review_status.json`), and advances its review cursor only after durable review accounting completes.

This two-plane model ensures that AI provider outages, context resets, or task terminations never affect the companion runtime or lose observation data, while enabling rich real-time developer awareness during active gameplay, crash-consistent replay safety, and complete post-session synthesis upon closure.

## What Changes

- **Subordinate Continuous Runtime Observation Tap**: Attach an asynchronous, non-blocking read-only observer (`DevelopmentObserver`) to `ContinuousRuntimeOrchestrator` lifecycle callbacks. The observer is strictly subordinate and never participates in or blocks the correctness path for `Client.txt` ingestion, `CharacterState` reconciliation, checkpoint persistence, objective evaluation, notification delivery, or writer lease ownership. When disabled, the observer creates no background worker and performs zero storage I/O, introducing only negligible callback branch check overhead.
- **Strict Single-Runtime Invariant**: The observer is not a second game runtime; it never instantiates a duplicate `ProcessMonitor`, `ClientLogTailer`, `CharacterStateStore` writer, or `ObjectiveEngine`.
- **Orderly Bounded Shutdown & Queue Drain Pipeline**: The observation session must never be marked `CLOSED` while queued evidence is unwritten. Shutdown enforces a strict 9-step sequence: (1) runtime initiates shutdown, (2) observer stops accepting new ordinary events, (3) bounded queue is drained, (4) pending screenshots are completed or cancelled/skipped, (5) JSONL writers are flushed and closed, (6) final counters and sequence watermarks reconcile, (7) session summary is generated, (8) manifest is atomically updated, and (9) only then may status become `CLOSED`. A bounded shutdown timeout (5.0s) guarantees the observer never blocks runtime shutdown indefinitely; if drain cannot finish within the timeout, the manifest is recorded as `INCOMPLETE` with `OBSERVER_DRAIN_TIMEOUT` and accurate pending/dropped counts, rather than claiming `CLOSED`.
- **Observer Health States & Worker Degradation**: Track explicit health states (`HEALTHY`, `DEGRADED`, `FAILED`). A fatal persistence worker failure never crashes the continuous runtime: observer health transitions to `FAILED`, new enqueues are rejected or safely discarded to prevent unbounded queue accumulation, and the manifest is marked `INCOMPLETE`. Screenshot worker failures degrade health to `DEGRADED` independently without disabling text/delta collection. Endless worker restart loops are forbidden.
- **Deterministic 3-Tier Priority Drop Policy**: Enforce deterministic queue shed behavior under backpressure:
  - `HIGH`: `ERROR`, parser anomalies, state deltas, user markers, objective changes
  - `MEDIUM`: notification decisions, ordinary parsed gameplay events
  - `LOW`: periodic performance telemetry, unchanged/no-op diagnostics
  When queue capacity is pressured, LOW evidence is dropped before MEDIUM before HIGH. If HIGH evidence must be dropped under extreme load, it is explicitly recorded in `dropped_high_priority_count` and data-loss metadata.
- **Correlation Integrity Under Dropped Evidence**: When upstream evidence (e.g. log observation A) is dropped under backpressure while downstream evidence (state delta B, objective trace C) survives, downstream envelopes record the dropped status or tombstone (`correlation_missing_due_to_backpressure`). Hermes review surfaces missing parent evidence under `MISSING_EVIDENCE` and prevents findings from being promoted beyond available support.
- **Canonical Evidence Envelope & Correlation Contract**: Define a stable evidence envelope across all observation streams featuring `schema_version`, unique `event_id`, strictly monotonic `sequence_number`, distinct `source_timestamp` and local `recorded_at`, fact taxonomy, and explicit `correlation_refs` linking the full causal chain: log observation -> state delta -> objective evaluation -> notification decision -> screenshot -> manual marker (forbidding loose heuristic timestamp matching).
- **Authoritative Marker IPC vs Persisted Marker Evidence**: Preserve the accepted cross-process marker architecture:
  - *Marker IPC*: `companion observe mark "<note>"` writes `runtime/observations/marker_inbox/<uuid>.tmp`, then executes an atomic rename to `<uuid>.json`. Concurrent CLI writers remain completely isolated via distinct UUID filenames. The continuous runtime `DevelopmentObserver` drains only complete `.json` files (ignoring `.tmp`), enriches them with active session and objective context, and reports inactive sessions honestly when no session is running.
  - *Persisted Marker Evidence*: The observer persists normalized marker evidence envelopes into `markers.jsonl` with full correlation metadata. Live analysis and Hermes consume this persisted evidence stream, NOT a shared append-only file as an IPC transport.
- **Fail-Closed Privacy for Log Anomaly Discovery**: Maintain strict filtering for whispers, chat channels, credentials, and tokens. Strengthen unknown-line discovery so representative text is persisted only when lines pass all filters, match an approved debug envelope, and sanitize completely. Any classification uncertainty triggers fail-closed behavior: representative text is withheld, setting `PRIVACY_SAMPLE_WITHHELD = true` and storing only normalized signature hashes, frequency counts, and timestamps.
- **Asynchronous Opt-In Screenshot Evidence**: Allow event-triggered screenshots (`--observe-screens`) via MSS with strict trigger filters, cooldowns, display targeting, and storage quotas. Capture requests are dispatched asynchronously to the observer worker so slow captures or failures (`SKIPPED_BUDGET`, `SKIPPED_COOLDOWN`, `CAPTURE_FAILED`) never block runtime ticks or mutate `CharacterState`.
- **Atomic Session Manifest & Manifest Reconciliation**: Maintain an atomically updated `session_manifest.json` tracking session status (`OPEN`, `CLOSED`, `INCOMPLETE`, `ABORTED`), high-watermark sequences, dropped event counts, and artifact counts. Total persisted records plus dropped events reconcile exactly against the sequence high watermark. Unfinalized prior sessions are safely detected on startup, marked `INCOMPLETE / ABORTED`, and preserved for partial post-session review.
- **Boundary Retention & Newly Closed Session Protection**: Enforce per-file JSONL rotation, screenshot quotas, and a deterministic global observation storage bound. Retention pruning executes strictly at session start, session close, or explicit CLI invocation (never during a gameplay tick). The active session, the session being finalized, and the newly closed session remain strictly protected through final summary/manifest completion, preventing premature deletion before review. Reports under `docs/audits/` are preserved permanently.
- **Observer Operational Performance Telemetry**: Measure enqueue latency, queue depth, dropped event count, writer latency, screenshot capture duration, and worker error counts using monotonic clock intervals.
- **Two-Plane Live Analysis Architecture (Local Data Plane vs Hermes AI Review Plane)**:
  - *Local Live Analysis Data Plane (`companion observe analyze-live`)*: A deterministic, read-only local process that reads newly appended evidence, manages stream continuity across rotated segments, maintains session correlation indexes, tracks persistent UNKNOWN state durations and churn metrics, records structured factual observations (`local_signals.jsonl`), updates durable reader cursor state (`reader_state.json`), and surfaces review candidate bundles. It runs independently of Hermes and has zero authority to mutate `CharacterState`, game runtime, or code.
  - *Hermes AI Review Plane*: When Hermes is invoked, it consumes unreviewed candidate bundles starting from its durable `hermes_review_cursor.json`, performs causal reasoning across multi-stream evidence, inspects raw local evidence or bounded windows of `Client.txt` when necessary, prioritizes user markers, and journals evaluated findings (`hermes_findings.jsonl`).
- **Crash-Consistent Local Reader, Contiguous Reader Frontier & Crash-Safe Read-Ahead**: The local reader executes under an at-least-once input and idempotent derived output contract: (1) read complete new observation records, (2) derive deterministic local signals and review bundles, (3) persist derived outputs durably to `local_signals.jsonl`, and (4) only after successful persistence, atomically advance `reader_cursor`. `reader_latest_sequence` strictly denotes the highest *contiguous* global observation sequence for which all evidence up to N is safely accounted for by the local analysis layer, NEVER the highest sequence number ever observed.
  - *Physical Per-Stream Read Positions vs Global Contiguous Frontier*: The system explicitly distinguishes physical per-stream read positions (`byte_offset`, `last_processed_sequence` per stream file) from the global contiguous analyzed frontier (`contiguous_frontier`). Because observation sequences are interleaved across multiple typed streams (`events`, `state_deltas`, `objective_traces`, `notification_traces`, `telemetry`, `markers`), a stream may advance physically ahead of the global frontier. To make read-ahead crash-safe without adding a database, durable reader state (`reader_state.json`) persists compact `accounted_ahead_ranges` (`[[start, end], ...]`) alongside per-stream byte offsets. On crash and restart, the reader reconstructs its ahead-sequence knowledge and stream positions, ensuring no un-frontiered evidence is skipped or lost, while duplicate replays remain safe and the contiguous frontier remains authoritative.
  - *Deterministic seen_ahead Saturation Policy*: The bounded read-ahead window (max 1000 ahead sequences) MUST NOT silently discard ahead sequence knowledge upon reaching capacity. When ahead sequences reach the configured capacity bound, the local reader applies a deterministic safe saturation policy: it stops additional read-ahead on ahead streams, keeps the safe contiguous frontier unchanged, waits for the lagging stream to emit `frontier + 1` (or for durable drop metadata/gap resolution), and exposes `ANALYST_READ_AHEAD_SATURATED`. Saturation pauses only the independent local analyzer; it never blocks `ContinuousRuntimeOrchestrator` or `DevelopmentObserver`. Once the missing sequence arrives, the frontier advances through the retained ahead range and reading resumes normally.
  - *Strict Gap Semantics*: If a sequence gap occurs (e.g. 91..94 and 96..100 processed, but 95 missing), the safe frontier remains at 94 until 95 is processed, explicitly dropped via durable metadata, or flagged as an approved gap. If output persistence fails, parsing fails, or `ANALYST_STREAM_GAP` occurs, `reader_cursor` strictly remains at the last safe contiguous position. Replayed records yield identical deterministic `local_signal_id` values, preventing duplicate logical signals. Incomplete trailing JSONL records remain unconsumed until flushed.
- **Crash-Consistent Hermes Review, Deterministic Review Batch Identity & Durable Results**: The Hermes review layer executes: (1) determine next pending evidence window past contiguous `review_cursor`, (2) compute deterministic batch identity, (3) check for existing completed batch result or invoke AI reasoning, (4) persist structured batch outcome to `live_analysis/review_batches/<review_batch_id>.json` and journal findings to `hermes_findings.jsonl`, and (5) atomically advance `hermes_review_cursor.json`.
  - *Deterministic Review Batch Identity*: To eliminate dependence on AI-generated wording or semantic keys for replay idempotency, the system computes a deterministic `review_batch_id` before invoking Hermes AI: `hash(session_id + contiguous_start_sequence + contiguous_end_sequence + ordered source evidence IDs)` derived strictly from structured evidence.
  - *Durable Review Batch Result Model*: Before advancing `review_cursor`, the review plane persists an atomic structured result in `live_analysis/review_batches/<review_batch_id>.json` recording `review_batch_id`, sequence range, reviewed evidence IDs, finding operations (`CREATE`, `UPDATE`, `NO_FINDING`), canonical finding keys, timestamp, and review status. Hidden chain-of-thought is never persisted.
  - *Finding Revision Idempotency*: Each finding revision records its source `review_batch_id`. Applying the SAME `review_batch_id` twice produces no duplicate revision, no doubled `occurrence_count`, and no duplicated `evidence_refs`. A NEW review batch with NEW corroborating evidence updates the existing finding and increments the revision once.
  - *Stable Logical Finding Key vs Mutable Evidence Set*: Logical finding ID is derived from `session_id`, finding `category`, and normalized semantic issue key (e.g. `find:{session_id}:{category}:{semantic_issue_key}`), NEVER from mutable evidence sets or generated prose.
  - *Replay Semantics on Resume*: If the next pending deterministic `review_batch_id` already has a valid completed durable review result (e.g. crash occurred after batch result write but before cursor advance), Hermes skips AI invocation, replays/applies the structured result idempotently, deduplicates finding revisions using `review_batch_id`, and advances `review_cursor` safely.
- **Finding Evolution vs New Finding**: Distinguish updating an existing finding from creating a new finding. When the same issue recurs or receives new corroborating evidence in a subsequent batch (e.g. F1 advances from `WATCHING` to `CORROBORATED`), the system updates the existing logical finding identity with structured history rather than creating duplicate findings F1, F2, F3.
- **Contiguous Review Cursor Semantics & Review-Batch Accounting**: `review_cursor` strictly denotes that "all reviewable evidence up to sequence N has completed durable Hermes review accounting" over a contiguous sequence range (never merely "Hermes read up to N"). It advances only over a contiguous reviewed/accounted range: if Hermes reviews 1..500 and 502..550 while 501 is pending, `review_cursor` remains at 500 until 501 completes. If findings persistence fails, the review cursor does not advance. When an evidence batch contains items reviewed with no finding warranted, lightweight review-batch metadata is recorded so the sequence advances safely without generating fabricated findings.
- **Heartbeat-Based Hermes Liveness Telemetry**: Hermes review liveness is tracked via `runtime/observations/<session>/live_analysis/hermes_review_status.json` containing `review_run_id`, `started_at`, `last_heartbeat`, `last_reviewed_sequence`, and `state` (`ACTIVE`, `IDLE`, `STOPPED`, `FAILED`). Hermes status is valid as `ACTIVE` only while an active review task is heartbeating within a fresh window. If the heartbeat expires, status is honestly displayed as `OFFLINE / INACTIVE / STALE`. Liveness is never inferred merely from the existence of `hermes_review_cursor.json` or old findings. The status file is pure telemetry and never acts as an ownership lock.
- **Provider Failure & Crash Recovery Cases**: The review layer handles failure deterministically across 4 explicit cases:
  - *Case A (Provider fails before durable review batch result exists)*: `review_cursor` remains unchanged, no completed batch result is written, and AI review retries on the next invocation.
  - *Case B (Durable review batch result exists but crash occurs before finding application completes)*: On resume, the system identifies the existing deterministic batch result, idempotently completes finding application without re-invoking AI, and advances `review_cursor`.
  - *Case C (Finding application completed but crash occurs before review_cursor advances)*: On resume, the batch result is found, finding revision idempotency prevents duplicate revisions or double counts, and `review_cursor` catches up cleanly.
  - *Case D (Review completed with NO_FINDING)*: Durable batch result records `NO_FINDING`, allowing `review_cursor` to advance safely without repeated AI calls or fake findings.
  Continuous runtime and observer continue completely unaffected across all failure scenarios.
- **Durable Stream Identity & Multi-Stream Continuity Contract**: `IncrementalStreamReader` tracks stream name, segment identity/filename, byte offset, last processed sequence, and timestamp across all typed streams. Validation uses sequence bounds and segment metadata without full-file hashing. On segment rotation, the reader finishes the old segment, advances monotonically to the next segment, validates sequence continuity, never re-reads consumed records, and never skips segments. Gap semantics explicitly distinguish: (1) temporarily unread records (holds contiguous frontier), (2) explicitly dropped sequences (accounted only via durable drop metadata like manifest `dropped_sequence_ranges`), (3) `ANALYST_STREAM_GAP` or missing segments (halts advance and reports degraded/gap state), and (4) duplicate sequences (deduplicated without corrupting the frontier).
- **Factual Local Signals vs AI Interpreted Findings**: The local analyzer produces only objective factual observations (e.g. UNKNOWN persisted for N seconds, objective reevaluated N times, notification queued N times, anomaly signature repeated N times, marker arrived, worker error). It never autonomously concludes `LIKELY_DEFECT`, `FEATURE_OPPORTUNITY`, or architectural recommendations without mechanical proof of invariant violation. High-level development interpretation belongs strictly to Hermes AI review.
- **Structured Live Analysis Journal Layout & Privacy Redaction**: Persist live analysis files under `runtime/observations/<session>/live_analysis/`: `reader_state.json`, `local_signals.jsonl`, `hermes_review_cursor.json`, `hermes_findings.jsonl`, `hermes_review_status.json`, and `review_batches/<review_batch_id>.json`. No hidden chain-of-thought is persisted. Hermes findings record only finding ID, classification, safe summary, evidence refs, frequency, corroboration, uncertainty, missing evidence, and updated timestamp. Private content is strictly redacted; findings cite only safe event IDs and pattern hashes.
- **Bounded Raw Client.txt Inspection**: When structured evidence is insufficient, Hermes may inspect raw `Client.txt` using bounded byte ranges or timestamp windows around known event offsets. Full-file rescans on polling cycles are strictly forbidden, and raw private chat or credentials must never be copied into findings or reports.
- **Three Distinct Sequence Lags, Saturation State & Review Batch Metrics**: `companion observe live-status` reports three distinct layers and two separate lag values based strictly on contiguous frontiers, never maximum-seen sequences:
  1. `observer_latest_sequence`: Highest sequence produced/accounted by continuous runtime observer.
  2. `reader_latest_sequence`: Highest contiguous safely analyzed sequence frontier, showing `reader_lag = observer_latest_sequence - reader_latest_sequence`. When read-ahead capacity is reached, displays reader saturation state (`ANALYST_READ_AHEAD_SATURATED`).
  3. `hermes_reviewed_sequence`: Highest contiguous durably reviewed sequence frontier, showing `review_lag = reader_latest_sequence - hermes_reviewed_sequence`. Displays completed and pending review batch counts.
  Lags are never collapsed into an ambiguous "analyst lag" and never use maximum-seen sequences across interleaved streams.
- **High-Priority Marker Escalation Across AI Availability**: Persisted player markers are classified as highest-priority review candidates. When Hermes is active, it reviews markers immediately. When Hermes is offline, markers are queued in local state as pending review; upon Hermes reconnection/resume, pending markers are processed before routine low-value telemetry. No marker is lost due to AI downtime.
- **Immediate Analysis Inception vs 30-Minute Acceptance Gate**: Real-time development analysis begins immediately at minute 0 upon session inception; actionable findings may emerge at minute 2, 5, or 10. The >=30-minute requirement serves solely as the minimum duration threshold for development-observation acceptance qualification, not as an artificial analysis delay.
- **Evidence-Grounded Hermes Review & Report Quality**: Establish strict evidence quality rules for post-session Hermes synthesis into `DEVELOPMENT_OBSERVATION_REPORT.md`. Candidate findings require concrete event ID citations, occurrence counts, time windows, and corroboration; isolated single anomalies without invariant violations remain `NOT ENOUGH EVIDENCE`. Live findings accumulated during play directly feed into the final report.
- **Separate Acceptance from Endurance and Recommendation Sufficiency**: A single continuous real gameplay observation of at least 30 minutes is the minimum development-observation acceptance duration; shorter sessions cannot be combined. A 60–120 minute endurance/stability soak is optional, not a prerequisite for every development observation. Duration alone is insufficient: final manifest and summary must agree on `CLOSED`, health must be `HEALTHY`, persisted plus dropped must equal the sequence high watermark, pending must be zero, sequence gaps and worker failures must be resolved, privacy audit must pass, and raw artifacts must remain local and ignored. Naturally absent gameplay events are `NOT OBSERVED`, not acceptance failures; recommendations dependent on absent evidence remain `NOT ENOUGH EVIDENCE` even when the observer passes.

## Capabilities

### New Capabilities
- `development-observation`: Read-only, privacy-safe development evidence collection, objective decision tracing, anomaly discovery, manual markers, bounded asynchronous storage, and post-session review packaging.

### Modified Capabilities
*(None - continuous runtime requirements and behavior remain unchanged when observation mode is disabled or attached).*

## Impact

- **Affected Code**:
  - `companion/runtime/orchestrator.py`: Register optional non-blocking `ObservationTap` callbacks and bounded shutdown/drain hook.
  - `companion/runtime/models.py`: Add observation configuration options (`observe_dev`, `observe_screens`, observation paths).
  - `companion/observe/` (new package): Core `DevelopmentObserver`, async worker, evidence models, storage manager, retention manager, privacy filter, marker inbox consumer, post-session summary generator, incremental stream reader (`reader.py`), dual-cursor managers (`cursor.py`), live development data-plane engine (`analyst.py`), and live findings journal (`journal.py`).
  - `companion/cli.py`: Add `--observe-dev` and `--observe-screens` flags to `runtime start`, plus `companion observe` CLI group (`mark`, `status`, `live-status`, `analyze-live`, `summary`, `review`, `cleanup`).
- **Dependencies**: Uses existing project dependencies (`pydantic`, `mss`, standard library `queue`, `threading`, `time`). No new runtime packages, OCR libraries, or AI dependencies.
- **Compliance & Safety**: Fully passive; zero game inputs; strictly local gitignored storage; no credential or private chat capture; fail-closed anomaly sampling; non-blocking bounded drain; crash-consistent replay deduplication; complete decoupling of AI provider availability from runtime stability.
